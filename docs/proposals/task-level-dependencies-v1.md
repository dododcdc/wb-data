# 方案：任务级前置依赖（V1）

> 状态：提案（核心语义已口头对齐，未立项实现）  
> 范围：离线「任务」与「任务」之间的前置依赖；不含画布内节点依赖（已有）  
> 引擎：Kestra **1.3.7**  
> 关联讨论：调度周期标记、同周期实例对齐、跨周期延后

---

## 1. 背景与结论

### 现状

| 层级 | 现状 |
|------|------|
| 任务内节点依赖 | 已有：画布边 → Kestra task `dependsOn` |
| 任务与任务依赖 | **无**：YAML 仅 `Schedule` 触发器，无任务级等待 |
| 调度配置 | Cron + 时区 + 启用；**无** `小时/天/月` 周期字段 |

### 方向（已对齐）

- **V1 只做同周期**：天→天、小时→小时（月→月可选）。
- **语义是「同期实例依赖」**，不是 Kestra 默认的「时间窗内有过成功」新鲜度模型。
- **调度改为周期优先**，并持久化 `period`；Cron 由周期生成；`CUSTOM` 不可配任务依赖。
- **跨周期**（天依赖小时「等哪一拍」）→ **V2**。
- 执行仍落在 Kestra 上，但产品规则由我们定义，再映射到 Schedule + 同期等待（见 §6），**不**假装裸 Flow 时间窗等于业务对齐。

一句话：

> 同周期按「计划业务期」对齐；真正开跑时间 = max(自己的计划时间, 所有前置同期实例完成时间)。

## 2. 目标与非目标

### 2.1 V1 目标

| ID | 能力 | 验收口径 |
|----|------|----------|
| G1 | 可为任务配置 1..N 个前置任务 | 配置可保存、推送后生效 |
| G2 | 仅同周期可配依赖 | 周期不一致时 UI/API 拒绝或不可选 |
| G3 | 同期实例依赖 + 启动时刻规则见 §3 | 用 §3.2 三例 + 「提前完成仍等自己计划点」验收 |
| G4 | 调度具备可靠周期语义 | 保存 `period` + 生成 Cron；依赖与调度共用该字段 |
| G5 | 每次执行带有稳定的**计划业务期**键 | 天=`日期`，小时=`日期+小时槽`；依赖按该键匹配 |
| G6 | 配置页能看到上游调度摘要 | 周期 + 计划时刻；智能推荐不做 |

### 2.2 非目标（V1 不做）

- Subflow 节点类型
- 跨周期依赖与「等齐当天全部小时实例」
- 智能推荐依赖
- 依赖失败策略大全（跳过、强制成功等）——V1：前置未成功则本任务该期**不往下执行业务**（可处于等待/未发出，运维可观测）
- 升级 Kestra 2.0

## 3. 场景边界与核心语义

### 3.1 V1 / V2 边界

| 场景 | 周期 | V1 | 说明 |
|------|------|----|------|
| 天 → 天 | 同 | ✅ | 主路径 |
| 小时 → 小时 | 同 | ✅ | 主路径 |
| 月 → 月 | 同 | ✅ 可选 | 对齐键为自然月 |
| 天 → 小时 | 跨 | ❌ V2 | 另定规则 |
| 小时 → 天 | 跨 | ❌ V2 | 另定规则 |
| 自定义 Cron ↔ 任意 | — | ❌ | 无可靠 `period` |
| 年调度 | — | ❌ | V1 不做入口 |

### 3.2 同周期语义（已拍板）

**对齐键（计划业务期）**

| 周期 | 对齐键 | 例子 |
|------|--------|------|
| 天 | 日历日（任务时区） | `2026-01-01` |
| 小时 | 日历日 + 小时槽 | `2026-01-01T11` |
| 月 | 年-月 | `2026-01` |

**规则**

1. A 在业务期 `K` 的这一次，必须等待每个前置任务在**同一个 `K`** 的实例达到 **SUCCESS**。  
2. **真正开始执行业务**的时间：

   \[
   start = \max(A\text{ 在 }K\text{ 的计划执行时间},\ \text{各前置在 }K\text{ 的完成时间})
   \]

3. 前置的计划钟点可以早于、等于或晚于 A；只认同一 `K`，不认「谁的 Cron 更早」。  
4. **前置若提前跑完，A 仍要等到自己的计划时间才启动**（不可因依赖提前而抢跑）。

**天任务示例**（A 计划 `2026-01-01 11:11:11`，依赖 B）

| B 在当天的计划时间 | 行为 |
|--------------------|------|
| `11:11:11` | B 未成功结束前，A 不能开跑 |
| `10:11:11` | 同上；若 B 10:30 已成功，A 仍等到 **11:11:11** 再开跑 |
| `12:11:11` | A 的 11:11 到点后若 B 未完，**继续等**；B 完成后 A 再开跑（晚于自己的计划时间，正常） |

小时任务同理：对齐的是同一个小时槽 `K`，不是「最近一次成功」。

### 3.3 与「Kestra 新鲜度窗」的区别

| | 同期实例（本方案 V1） | 时间窗新鲜度（Kestra 默认直觉） |
|--|----------------------|----------------------------------|
| 匹配 | 同一计划业务期 `K` | 某段墙上时钟内任意 SUCCESS |
| 启动 | max(自己计划点, 前置完成) | 条件一满足就触发（易抢跑） |
| 文案 | 可以说「等同期的 B」 | 「窗内 B 成功过即可」 |

V1 **采用左列**。UI/文档按「同期 / 计划业务期」表述即可。

## 4. 调度配置改造（V1 配套）

依赖要同周期校验，且要能算出计划业务期 `K`，调度必须回答「小时还是天」。

### 4.1 UI

- **主路径**：选周期 `小时 | 天 | 月`，再选具体时刻。  
- 生成 Cron 写入现有 schedule，供 Kestra `Schedule` 使用。  
- **高级 Cron**：V1 建议隐藏；若保留 → `period=CUSTOM`，**禁止**任务级依赖。  
- 「启用自动调度」= 草稿意图；**推送远程后才生效**。

### 4.2 数据

```text
period: HOURLY | DAILY | MONTHLY | CUSTOM
cron:   string
timezone: string
enabled: boolean
```

`period` 为依赖校验与 `K` 计算的主键；禁止仅靠解析 Cron 作为唯一来源（迁移推断除外）。

### 4.3 已有任务迁移

1. 能唯一推断 → `HOURLY` / `DAILY` / `MONTHLY`。  
2. 否则 → `CUSTOM`；可调度，不可配任务依赖。

## 6. 编译 / 运行时映射（Kestra 1.3.7）

产品语义已定；实现要同时满足「到点」和「不抢跑」，**不能**只用「Schedule 与 Flow 各火一次」的双触发。

### 6.1 推荐运行模型（V1）

对业务期 `K` 的一次运行：

1. **到点**：由本任务 `Schedule` 在计划时间产生（或唤醒）该期执行意图。  
2. **闸门**：执行业务节点之前，等待所有前置在同一 `K` 上 SUCCESS。  
3. **前置晚于自己**：闸门一直等到前置完成，再继续（晚启动）。  
4. **前置早于自己**：到点时前置已 SUCCESS → 闸门立即通过，**按计划点开跑**（不提前）。

因此：

- **有依赖时**：Schedule 负责「最早可启动的计划点」；依赖负责「同期是否齐」。  
- **不要**再用单独的 Flow Trigger 在上游一成功就另起一条 execution（会抢跑或一天两次）。

### 6.2 计划业务期如何进 Kestra

每次调度触发写入稳定标签或 input，例如：

```text
wb.period = DAILY
wb.scheduleKey = 2026-01-01          # 天
# 或 HOURLY: 2026-01-01T11
```

`scheduleKey` 由计划执行时间按 `period` + 时区计算，**不要**用实际启动时间倒推（否则延迟启动会错期）。

闸门查询前置：同 namespace 映射下，前置 Flow 是否存在 `wb.scheduleKey = K` 且状态 SUCCESS。

### 6.3 实现备选（实现阶段再选，产品语义不变）

| 方案 | 做法 | 备注 |
|------|------|------|
| A | Schedule 到点创建 execution → 首部 `Pause`/等待任务轮询前置同期 SUCCESS | 最贴语义；注意等待超时与运维展示 |
| B | wb-data 侧依赖服务：到点且齐了才调 Kestra 执行 | 产品可控；要自建到点调度与防重 |
| C | 仅 Flow Trigger + 上游成功后 sleep 到自己计划点 | 多前置与失败重跑易复杂，V1 不优先 |

文档不锁死 A/B，但 **禁止** 无闸门的裸双触发。

### 6.4 不做 Subflow

依赖不进画布 DAG，不新增节点类型。

## 9. 风险

| 风险 | 缓解 |
|------|------|
| 用错 Kestra 时间窗当成同期对齐 | 按 §3 / §6 验收；单测覆盖三例 + 不抢跑 |
| 用实际启动时间算 `K` 导致错期 | `K` 只来自**计划**执行时间 |
| 等待任务占资源 / 超时策略不清 | P2 定超时与告警；运维展示「等待前置」 |
| `CUSTOM` 无法配依赖 | 引导改为标准周期 |
| 1.3.7 API 与 2.0 文档混用 | 以本机插件 schema 为准 |
