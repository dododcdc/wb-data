# 方案：任务级前置依赖（V1）

> 状态：P1 调度配置已实现；P2 模型与校验规则已定稿（2026-09-17），待实现
> 范围：离线「任务」与「任务」之间的前置依赖；不含画布内节点依赖（已有）  
> 引擎：Kestra **1.3.7**  
> 关联讨论：调度频率标记、同周期实例对齐、跨周期延后

---

## 1. 背景与结论

### 现状

| 层级 | 现状 |
|------|------|
| 任务内节点依赖 | 已有：画布边 → Kestra task `dependsOn` |
| 任务与任务依赖 | **无**：YAML 仅 `Schedule` 触发器，无任务级等待 |
| 调度配置 | 调度频率（每小时/每天/每周/每月/每年）+ 计划时间 + 启用；时区绑定任务，Cron 自动生成 |

### 方向（已对齐）

- **V1 只做同周期**：周期集合固定为 `小时 | 天 | 周 | 月 | 年`，仅同周期可配依赖。
- **语义是「同期实例依赖」**，不是 Kestra 默认的「时间窗内有过成功」新鲜度模型。
- **调度改为频率优先**，并持久化 `period`；Cron 由调度频率与计划时间生成；**不提供自定义 Cron 入口**（2026-09-15 拍板），存量非标准 Cron 仅保留 `CUSTOM` 标记并在编辑时引导选择标准调度频率。
- **跨周期**（天依赖小时「等哪一拍」）→ **V2**。
- 执行仍落在 Kestra 上，但产品规则由我们定义，再映射到 Schedule + 同期等待（见 §6），**不**假装裸 Flow 时间窗等于业务对齐。

一句话：

> 同周期按「计划业务期」对齐；真正开跑时间 = max(自己的计划时间, 所有前置同期实例完成时间)。

### 术语约定（2026-09-16）

| 术语 | 含义 | 示例 |
|------|------|------|
| 调度频率 | 多久触发一次，界面字段名称 | 每小时、每天、每周、每月、每年 |
| 周期 | 用于业务期划分的时间粒度，不是运行轮次 | 小时、天、周、月、年 |
| 计划业务期 | 按计划执行时间、周期与任务时区确定的具体一期，以 `scheduleKey` 标识 | 每天任务的 `2026-09-16`、每周任务的 `2026-W38` |
| 运行实例 | 一次实际执行，不等同于业务期 | 同一业务期重跑可产生多个运行实例 |

V1 标准调度频率与业务期粒度一一对应，沿用内部 `period` 字段，不改 API、YAML 标签或对齐键规则。文档中的「同周期 / 跨周期依赖」保留为业务期粒度约束；「同期」指同一个计划业务期，不按运行次数对齐。

## 2. 目标与非目标

### 2.1 V1 目标

| ID | 能力 | 验收口径 |
|----|------|----------|
| G1 | 可为任务配置 1..N 个前置任务，允许跨项目组 | 配置可保存、推送后生效 |
| G2 | 仅同周期可配依赖（跨组也不例外） | 周期不一致时 UI/API 拒绝或不可选 |
| G3 | 同期实例依赖 + 启动时刻规则见 §3 | 用 §3.2 三例 + 「提前完成仍等自己计划点」验收 |
| G4 | 调度具备可靠周期语义 | 保存 `period` + 生成 Cron；依赖与调度共用该字段 |
| G5 | 每次执行带有稳定的**计划业务期**键 | 天=`日期`，小时=`日期+小时槽`；依赖按该键匹配 |
| G6 | 配置页能看到上游调度摘要 | 调度频率 + 计划时间；智能推荐不做 |

### 2.2 非目标（V1 不做）

- Subflow 节点类型
- 跨周期依赖与「等齐当天全部小时实例」
- 智能推荐依赖
- 依赖失败策略大全（跳过、强制成功等）——V1：前置未成功则本任务该期**不往下执行业务**（可处于等待/未发出，运维可观测）
- 升级 Kestra 2.0

## 3. 场景边界与核心语义

### 3.1 V1 / V2 边界

| 场景 | 周期 | V1 | 说明 |
|------|------|----|------|
| 天 → 天 | 同 | ✅ | 主路径 |
| 小时 → 小时 | 同 | ✅ | 主路径 |
| 周 → 周 | 同 | ✅ | 对齐键为 ISO 周 |
| 月 → 月 | 同 | ✅ | 对齐键为自然月 |
| 年 → 年 | 同 | ✅ | 对齐键为日历年 |
| 天 → 小时 | 跨 | ❌ V2 | 另定规则 |
| 小时 → 天 | 跨 | ❌ V2 | 另定规则 |
| 自定义 Cron ↔ 任意 | — | ❌ | 入口已去掉；存量仅保留 `CUSTOM` 标记，编辑时引导覆盖 |

### 3.2 同周期语义（已拍板）

**对齐键（计划业务期）**

| 周期 | 对齐键 | 例子 |
|------|--------|------|
| 天 | 日历日（任务时区） | `2026-01-01` |
| 小时 | 日历日 + 小时槽 | `2026-01-01T11` |
| 周 | ISO 周（基于周的年 + 周序） | `2026-W01` |
| 月 | 年-月 | `2026-01` |
| 年 | 日历年 | `2026` |

**规则**

1. A 在业务期 `K` 的这一次，必须等待每个前置任务在**同一个 `K`** 的实例达到 **SUCCESS**。  
2. **真正开始执行业务**的时间：

   \[
   start = \max(A\text{ 在 }K\text{ 的计划执行时间},\ \text{各前置在 }K\text{ 的完成时间})
   \]

3. 前置的计划钟点可以早于、等于或晚于 A；只认同一 `K`，不认「谁的 Cron 更早」。  
4. **前置若提前跑完，A 仍要等到自己的计划时间才启动**（不可因依赖提前而抢跑）。

**天任务示例**（A 计划 `2026-01-01 11:11:11`，依赖 B）

| B 在当天的计划时间 | 行为 |
|--------------------|------|
| `11:11:11` | B 未成功结束前，A 不能开跑 |
| `10:11:11` | 同上；若 B 10:30 已成功，A 仍等到 **11:11:11** 再开跑 |
| `12:11:11` | A 的 11:11 到点后若 B 未完，**继续等**；B 完成后 A 再开跑（晚于自己的计划时间，正常） |

小时任务同理：对齐的是同一个小时槽 `K`，不是「最近一次成功」。

### 3.3 与「Kestra 新鲜度窗」的区别

| | 同期实例（本方案 V1） | 时间窗新鲜度（Kestra 默认直觉） |
|--|----------------------|----------------------------------|
| 匹配 | 同一计划业务期 `K` | 某段墙上时钟内任意 SUCCESS |
| 启动 | max(自己计划点, 前置完成) | 条件一满足就触发（易抢跑） |
| 文案 | 可以说「等同期的 B」 | 「窗内 B 成功过即可」 |

V1 **采用左列**。UI/文档按「同期 / 计划业务期」表述即可。

## 4. 调度配置改造（V1 配套）

依赖要同周期校验，且要能算出计划业务期 `K`，调度必须回答「小时还是天」。

### 4.1 UI

- **主路径**：选择「调度频率」`每小时 | 每天 | 每周 | 每月 | 每年`，再选计划时间（每周 = 星期几 + 时刻；每年 = 月 + 日 + 时刻）。
- 生成 Cron 写入现有 schedule，供 Kestra `Schedule` 使用。
- **自定义 Cron 入口已去掉**（2026-09-15 拍板）；存量非标准 Cron 打开调度弹窗时提示，选择标准调度频率并暂存后覆盖。
- 「自动调度」开关 = 草稿意图；暂存后需保存、提交并推送，**同步成功后生效**。

### 4.2 数据

```text
period: HOURLY | DAILY | WEEKLY | MONTHLY | YEARLY | CUSTOM
cron:   string
timezone: string
enabled: boolean
```

`period` 为依赖校验与 `K` 计算的主键；禁止仅靠解析 Cron 作为唯一来源（迁移推断除外）。`CUSTOM` 仅作存量非标准标记，界面不可选、不可配任务依赖。

### 4.3 已有任务迁移

1. 能唯一推断 → `HOURLY` / `DAILY` / `WEEKLY` / `MONTHLY` / `YEARLY`。  
2. 否则 → `CUSTOM`；可调度，不可配任务依赖，编辑时引导覆盖为标准调度频率。

## 5. 依赖模型与校验规则（2026-09-17 定稿）

### 5.1 任务标识与跨组依赖

- 任务全局标识 = **项目组 + 任务**（`groupId + flowId`）；Kestra 侧映射为 namespace `pg-<groupId>` + flow id。
- **允许跨项目组依赖**（2026-09-17 拍板）：数据接入组 → 加工组是主场景，「仅同项目组」不是约束。
- 跨组仍仅限**相同调度频率、同一业务期**；跨周期一律 V2。
- 引用 ≠ 编辑：跨组只能依赖自己**有权查看**的任务，不能因此获得上游项目的编辑权。

### 5.2 数据模型

**存储**：写入任务 YAML 的 `labels`（Kestra 原生字段，不引入未知根字段，避免推送校验失败），随 Git 推送生效：

```yaml
labels:
  wbdataSchedulePeriod: DAILY                      # 已有（P1）
  wbdataDependencies: "3:ods_user,4:ods_order"     # <groupId>:<flowId> 逗号分隔；缺省 = 无依赖
  wbdataFailurePolicy: CONTINUE                    # CONTINUE | PAUSE；缺省 = CONTINUE
  wbdataCrossGroupDependency: ALLOW                # ALLOW | DENY；缺省 = ALLOW（是否允许被跨组依赖）
```

**API DTO**（草稿/保存用结构化形式，与 labels 的互转由后端负责）：

```text
dependencies: [{ groupId: number, flowId: string }]   # 0..N
failurePolicy: CONTINUE | PAUSE                        # 默认 CONTINUE
crossGroupDependency: ALLOW | DENY                     # 默认 ALLOW；创建任务时可指定，创建后可调整
```

### 5.3 保存校验规则（API 强制；UI 过滤仅作体验）

| # | 规则 | 违反时 |
|---|------|--------|
| R1 | 不允许依赖自身（同 `groupId + flowId`） | 拒绝 |
| R2 | 上游任务必须存在，且当前用户对其项目组有查看权限 | 拒绝 |
| R3 | **同频率**：上游与本任务 `period` 相同；判定只看 `period` 字段，**不比对 Cron 字符串** | 拒绝 / 不可选 |
| R4 | 双方 `period` 均不得为 `CUSTOM`；上游必须已配置标准调度（无调度则无计划业务期，依赖将永远等待） | 拒绝 / 不可选 |
| R5 | **无环**：在「现有依赖图 + 本次变更」上检测直接与间接环，跨组回环同样拦截；检测范围限于用户有权引用的任务图，不为找环暴露无权项目内容 | 拒绝 |
| R6 | 依赖列表去重；V1 前置数量上限 20 | 拒绝 |
| R7 | **跨组依赖须上游允许**：仅当 `groupId` 与本任务不同且上游 `crossGroupDependency = DENY` 时拦截；同组依赖不受此开关限制 | 拒绝 / 不可选 |

**所有校验在保存提交时复核**（不轻信打开弹窗时的快照），防止两个窗口并发操作绕过。

「允许跨组被依赖」开关的理由：P1/P2 让「被依赖」有实际代价（删除、改频率被锁），上游团队需要拒绝权；默认 `ALLOW` 避免接入组主场景每个任务都要先手动开启。

### 5.4 上游保护规则（2026-09-17 拍板）

| # | 场景 | 行为 |
|---|------|------|
| P1 | 删除任务 A，且存在下游依赖 A | 提醒并**禁止**；列出下游任务，须先解除依赖 |
| P2 | 修改 A 的调度频率，导致现有下游不再同频率 | 提醒并**禁止**；同频率下仅改计划时间允许 |
| P3 | 解除依赖只能由**下游方**操作（编辑自己的依赖列表），上游不能单方面摘除 | — |
| P4 | 删除 / 改频率在提交时重新全量校验影响面，防并发窗口绕过 | — |
| P5 | 把 A 的跨组依赖开关改为 `DENY`，且已存在跨组下游 | 提醒并**禁止**；须先解除跨组依赖（同组下游不受影响） |

### 5.5 上一期失败策略（任务自身，与依赖闸门独立）

以天任务 A 为例：A 在 `2026-01-01` 失败，`2026-01-02` 到点时——

| 策略 | 行为 |
|------|------|
| `CONTINUE`（默认） | 上一期失败只产生失败实例，下一期正常到点启动；一次失败不堵死后续每天 |
| `PAUSE` | 上一期终态非 SUCCESS 时，下一期到点不启动业务，标记暂停；人工重跑成功或手动恢复后，后续期恢复正常 |

规则：

1. 只控制 **A 自己**下一期是否启动；
2. 下游 B 始终等待 A **同期** SUCCESS，不受此开关旁路；
3. 手动 / debug 执行旁路该策略（与旁路依赖闸门一致）；
4. V1 只做这两个选项，不引入跳过、强制成功、补数窗口。

### 5.6 配置界面要点（细节交互步骤 3 再定）

1. 跨组搜索选择前置任务，列表按 R1–R4 过滤。
2. 展示上游：项目组、任务名、调度频率、计划时间摘要。
3. 删除 / 改频率被 P1 / P2 拦截时，给出下游清单与「先解除依赖」引导。
4. 智能推荐：不做。

## 6. 编译 / 运行时映射（Kestra 1.3.7）

产品语义已定；实现要同时满足「到点」和「不抢跑」，**不能**只用「Schedule 与 Flow 各火一次」的双触发。

### 6.1 推荐运行模型（V1）

对业务期 `K` 的一次运行：

1. **到点**：由本任务 `Schedule` 在计划时间产生（或唤醒）该期执行意图。  
2. **闸门**：执行业务节点之前，等待所有前置在同一 `K` 上 SUCCESS。  
3. **前置晚于自己**：闸门一直等到前置完成，再继续（晚启动）。  
4. **前置早于自己**：到点时前置已 SUCCESS → 闸门立即通过，**按计划点开跑**（不提前）。

因此：

- **有依赖时**：Schedule 负责「最早可启动的计划点」；依赖负责「同期是否齐」。  
- **不要**再用单独的 Flow Trigger 在上游一成功就另起一条 execution（会抢跑或一天两次）。

### 6.2 计划业务期如何进 Kestra

每次调度触发写入稳定标签或 input，例如：

```text
wb.period = DAILY
wb.scheduleKey = 2026-01-01          # 天
# 或 HOURLY: 2026-01-01T11
```

`scheduleKey` 由计划执行时间按 `period` + 时区计算，**不要**用实际启动时间倒推（否则延迟启动会错期）。

闸门查询前置：同 namespace 映射下，前置 Flow 是否存在 `wb.scheduleKey = K` 且状态 SUCCESS。

### 6.3 实现方案（A 已拍板，2026-09-17）

| 方案 | 做法 | 备注 |
|------|------|------|
| **A（选定）** | Schedule 到点创建 execution → 首部 `LoopUntil` 轮询前置同期 SUCCESS（按 label 过滤 executions） | 最贴语义；注意等待超时与运维展示 |
| B | wb-data 侧依赖服务：到点且齐了才调 Kestra 执行 | 产品可控；要自建到点调度与防重 |
| C | 仅 Flow Trigger + 上游成功后 sleep 到自己计划点 | 多前置与失败重跑易复杂，V1 不优先 |

采用方案 A 的拉模型；升 Kestra 2.x 不改变主体结构。**禁止**无闸门的裸双触发。上一期失败策略（§5.5）在同一首部闸门之前独立判断。

### 6.4 不做 Subflow

依赖不进画布 DAG，不新增节点类型。

## 9. 风险

| 风险 | 缓解 |
|------|------|
| 用错 Kestra 时间窗当成同期对齐 | 按 §3 / §6 验收；单测覆盖三例 + 不抢跑 |

| `CUSTOM` 无法配依赖 | 引导改为标准调度频率 |
| 1.3.7 API 与 2.0 文档混用 | 以本机插件 schema 为准 |
