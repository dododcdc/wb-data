# 离线开发提交流程范围重构设计

## 背景

当前离线开发界面的“提交”按钮位于 Flow 画布工具栏中，点击前还会自动保存当前打开的 Flow，因此用户自然会把它理解为“提交当前 Flow”。

但现有后端实现实际执行的是整仓库级别的 Git 提交：

- `git status --porcelain`
- `git add -A`
- `git commit -m`

这会导致当前项目组离线仓库内其它 Flow、目录、布局、脚本等已落盘改动一并进入本次 commit，和界面语义不一致，存在误提交风险。

同时，当前 `Push` 按钮的权限门槛也是 `offline.write`，并非项目管理员专用。仓库级提交与推送都属于高影响范围的仓库级操作，应该使用比 Flow 编辑更严格的权限模型。

## 目标

1. 让画布内“提交”严格表示“提交当前 Flow”。
2. 保留整仓库提交能力，用于文件夹操作、跨 Flow 修改等仓库级改动。
3. 将整仓库提交与 Push 一起收敛为项目管理员专用能力。
4. 让前端入口、权限模型、后端实际提交范围保持一致。

## 非目标

1. 不引入“部分选择文件提交”的通用 Git UI。
2. 不改变现有 Flow 保存、执行、调度的业务语义。
3. 不改造远程仓库模型或 Push 协议。

## 设计结论

离线开发界面拆分为两类提交入口：

1. **提交当前 Flow**：保留在 Flow 画布工具栏中，仅提交当前 Flow 关联文件。
2. **提交仓库改动**：新增在侧边栏工具区、紧邻 `Push` 按钮，仅项目管理员可用，提交当前项目组离线仓库内所有已落盘改动。

同时，`Push` 也调整为仅项目管理员可用。

## 入口与权限设计

### 提交当前 Flow

- 位置：保持在当前 Flow 画布工具栏。
- 适用对象：具备 `offline.write` 的用户。
- 前置条件：当前存在活动 Flow。
- 语义：只提交当前 Flow 的关联文件，不包含其它 Flow 或仓库中无关改动。

### 提交仓库改动

- 位置：放在侧边栏仓库工具区，紧邻 `Push` 按钮。
- 适用对象：仅项目管理员。
- 权限门槛：
  - 前端：使用项目管理员对应的明确信号判断，优先采用 `group.settings` 权限或 `currentGroup.role === GROUP_ADMIN`，避免继续使用 `offline.write` 混淆管理员与开发者。
  - 后端：接口权限要求提升到项目管理员级别，拒绝非管理员直调。
- 语义：提交当前项目组离线仓库内所有已落盘改动。

### Push

- 位置：保持不变。
- 适用对象：改为仅项目管理员。
- 语义：将当前项目组离线仓库推送到远程仓库。

## 行为设计

### 提交当前 Flow

点击后按以下顺序执行：

1. 如果当前 Flow 有未保存改动，先沿用现有逻辑自动保存当前 Flow。
2. 若保存失败或发生冲突，停留在保存冲突/错误处理流程，不进入提交。
3. 保存成功后弹出“提交当前 Flow”对话框。
4. 用户填写提交说明并确认。
5. 前端调用新的 scoped commit 接口，传入 `groupId`、`flowPath`、`message`。
6. 后端仅提交当前 Flow 关联文件。

对话框文案应明确说明本次提交范围，例如：

> 本次只提交当前 Flow 的定义、脚本和布局文件，其它未提交改动不会进入这次提交。

### 提交仓库改动

点击后按以下顺序执行：

1. 如果管理员当前正打开一个 Flow 且存在未保存改动，先自动保存当前 Flow。
2. 若保存失败或冲突，则停留在相应处理流程，不进入仓库级提交。
3. 保存成功后弹出“提交仓库改动”对话框。
4. 用户填写提交说明并确认。
5. 前端调用新的 repo commit 接口，传入 `groupId`、`message`。
6. 后端执行整仓库提交。

对话框文案应明确说明范围，例如：

> 会提交当前项目组离线仓库内所有已落盘改动。

## 当前 Flow 的提交边界

“当前 Flow”不是单一文件，提交范围必须基于 Flow 的实际文件集合，而不是仅按 `flow.yaml` 或目录名猜测。

当前 Flow 的提交范围定义为：

1. 当前 `flowPath` 对应的 `flow.yaml`
2. 同目录下的 `.layout.json`
3. 当前 Flow 中所有节点引用的 `scriptPath`

后端应复用现有 Flow 文档解析能力来解析这组文件，避免前后端各自维护一份不一致的文件映射逻辑。

## 接口设计

### 1. scoped commit：提交当前 Flow

新增或改造接口为：

- 入参：`groupId`、`flowPath`、`message`
- 权限：`offline.write`
- 行为：仅提交当前 Flow 关联文件

后端提交流程：

1. 解析当前 Flow 文件集合。
2. 基于这些路径检查 scoped diff。
3. 对这些路径执行带范围的 `git add -A -- <paths...>`。
4. 仅在这些路径存在改动时执行提交。

为避免 Git index 中已有其它已暂存文件被一并带入 commit，需要增加保护逻辑：

- 如果检测到 index 中存在不属于当前 Flow 的已暂存内容，则拒绝本次 scoped commit，并返回明确错误，要求用户先完成或清理仓库级暂存。

这样可以保证“提交当前 Flow”在语义上真正隔离。

### 2. repo commit：提交仓库改动

新增接口或保留现有接口语义为：

- 入参：`groupId`、`message`
- 权限：项目管理员
- 行为：整仓库提交

后端继续执行整仓库级 Git 提交，适用于：

- 文件夹创建、删除、重命名
- Flow 删除或重命名带来的跨目录调整
- 多个 Flow 的批量改动
- 其它不适合映射到单个 Flow 的仓库级改动

### 3. push repo：推送仓库

现有 push 接口保持整仓库语义，但权限提升为项目管理员。

## 前端设计

### 按钮与文案

- 画布工具栏中的“提交”重命名为 **提交当前 Flow**
- 侧边栏、`Push` 按钮旁新增 **提交仓库改动**
- 提交对话框标题与说明文案分别对应 Flow 级与仓库级语义

### 显示与禁用逻辑

#### 提交当前 Flow

- 需要存在活动 Flow
- 需要具备 `offline.write`
- 需要当前 Flow 范围内存在可提交改动

#### 提交仓库改动

- 仅项目管理员可见
- 当仓库存在已落盘改动时可用
- 不依赖当前是否打开某个 Flow

#### Push

- 仅项目管理员可见
- 保持现有 loading / disabled 逻辑

### 状态来源

当前 UI 中 `repoStatus.dirty` 是整仓库级状态，不适合直接驱动“提交当前 Flow”的红点和可点击状态。

因此需要补充当前 Flow 范围状态来源。可选实现方式：

1. 新增 Flow scoped status 接口，返回当前 Flow 是否存在未提交改动。
2. 在打开/保存 Flow 后，由后端返回当前 Flow 范围状态并缓存。

推荐新增明确的 scoped status 能力，避免前端猜测文件范围。

## 后端设计

### 权限模型

- `offline.write`：保留给 Flow 编辑、保存、当前 Flow 提交
- 项目管理员（建议基于 `group.settings` / `GROUP_ADMIN`）：
  - 提交仓库改动
  - Push

### Git 行为约束

#### 当前 Flow 提交

- 只允许提交当前 Flow 关联文件
- 必须显式防止其它已暂存内容被提交
- 若当前 Flow 范围无改动，返回“暂无改动需提交”

#### 仓库级提交

- 延续当前整仓库行为
- 若仓库无改动，返回“暂无改动需提交”

## 错误处理

### 当前 Flow 提交

- 自动保存失败：沿用现有保存失败反馈
- 保存冲突：沿用现有冲突对话框
- scoped diff 为空：提示当前 Flow 暂无可提交改动
- 存在不属于当前 Flow 的已暂存内容：提示无法执行当前 Flow 提交，并引导使用仓库级提交或先清理暂存

### 仓库级提交

- 自动保存失败：沿用现有保存失败反馈
- 仓库无改动：提示暂无改动需提交
- 权限不足：返回明确的权限错误

### Push

- 权限不足：返回明确的权限错误
- 其余错误保持现有推送失败反馈策略

## 测试设计

### 前端

1. 开发者可见并可使用“提交当前 Flow”
2. 开发者不可见“提交仓库改动”和 `Push`
3. 项目管理员可见并可使用“提交仓库改动”和 `Push`
4. 点击“提交当前 Flow”时会先自动保存当前 Flow
5. 点击“提交仓库改动”时，如果当前 Flow 脏，也会先自动保存当前 Flow
6. 两类提交对话框展示正确文案

### 后端

1. 当前 Flow 提交仅提交该 Flow 关联文件
2. 当前 Flow 提交不会带上其它 Flow 改动
3. 当前 Flow 提交在存在越界已暂存内容时会被拒绝
4. 仓库级提交会提交整仓库已落盘改动
5. 非管理员调用仓库级提交与 Push 会被拒绝

## 实施顺序

1. 明确并实现项目管理员权限判断
2. 新增当前 Flow scoped commit 能力
3. 拆分 repo commit 能力并提升权限门槛
4. 前端拆分按钮与弹窗文案
5. 增补 scoped 状态来源，修正按钮红点与禁用逻辑
6. 完成前后端测试覆盖

## 预期结果

改造完成后：

- 画布里的提交按钮与实际行为一致，不再误提交流程外改动
- 仓库级提交与 Push 统一放在仓库工具区，并统一为项目管理员能力
- Flow 编辑能力与仓库级发布能力边界清晰，降低误操作风险
